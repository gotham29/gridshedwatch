Early warning of grid load sheds, scored like weather warnings

Since 2020, US grid operators have had to cut power for lack of supply eight times. The public was warned beforehand in four. GridShedWatch is a shared test of whether a warning method would have caught them in time: all eight events, public hourly data, and one fixed scoring procedure any method can be run through.

Why a benchmark

Plenty of methods claim to spot grid trouble early. None of them can be compared, because there has been no common test.

What exists

  • Seasonal reliability assessments (NERC) and operators' own alert levels, set by judgment.
  • Anomaly-detection studies on simulated grids, or on one event, scored per hour.
  • No public list of real load sheds with a fixed way to score warnings against them.

What GridShedWatch adds

  • Every qualifying load shed since 2020, chosen by a stated rule, not by hand.
  • The same data, rules and alert budget for every method, so only the method differs.
  • The operators' own public notices as the baseline to beat.

How it is scored

The National Weather Service scores every warning on three numbers read together: events warned in advance, lead time, and false alarms. GridShedWatch asks the same of grid warnings, at two levels.

Watch

Something unusual is building

About one a month per grid. Counts if an alert starts in the 7 days before the load shed begins.

Warning

Act now

Two a year per grid. Counts from 7 days before onset to 48 hours after, since a warning during the event still helps.

The rules every method shares

  • A method only scores each hour. For each of five signals from EIA-930 (demand forecast error, demand minus generation, and seasonal anomalies of demand, generation and their gap) it says how unusual the hour is, from 0 to 1, using data up to that hour only.
  • One shared rule turns scores into alerts. Both signal groups must be unusual at once and stay so for a few hours. The rule is the same for every method.
  • Same alert budget, set without the events. Each method's threshold and persistence are chosen so it raises at most 12 watches and 2 warnings per grid per year, looking only at alert counts.
  • Read against chance. Each method's own alerts are shifted to random times 2,000 times to show how many events it would catch by luck. Intervals come from resampling the events.

Full protocol: docs/scoring.md.

The eight events

Every operator-initiated load shed caused by too little supply in a grid that reports to EIA-930, January 2020 to September 2026, of at least 250 MW at its worst. Three events were used to design the shared rules; five were held out and scored once.

Add your method

Two ways in. Both are scored the same way, at the same alert budget.

Scores track

The controlled comparison. Your method scores how unusual each of the five signals is, every hour. The shared rules, the budget step and the scoring are done for you, so it cannot be tuned toward the eight events. All five reference methods are here.

Alerts track

Any method that decides on its own when to alert: a rule, a classifier, a weather-based model, a forecaster's judgment. List when each watch and warning started. Any data available at the time is allowed.

A worked example, in three steps

Say your method is a simple rule of your own: raise a watch when demand has run unusually far above its forecast for three hours, and a warning when it has done so badly for six (examples/my_alerts.py).

1. Run it over the data and write down when each alert started, one line per alert (add a seed column if your method is random):

grid,level,start_utc
tx,watch,2021-02-09 12:00
tx,warning,2021-02-09 21:00
duk,watch,2022-12-24 00:00
...

2. Score it:

pip install gridshedwatch
gridshedwatch score-alerts my_alerts.csv --name "My rule"

3. Read the result:

My rule  (1 seed)
  watch    submitted alerts   caught 3.0 of 8 [1.0-5.0], chance 0.9; held-out 2.0 of 5;
                              median lead 131.0 h; 5.7 alerts/grid/yr; false alarm ratio 99%
  warning  submitted alerts   caught 1.0 of 8 [0.0-3.0], chance 0.1; held-out 0.0 of 5;
                              median lead 130.0 h; 0.6 alerts/grid/yr; false alarm ratio 97%

The rule watched 3 of the 8 load sheds, where its alerts at random times would have caught about one, and warned Texas five days before Uri. It missed the rest. A method in the scores track hands over its hourly scores instead (my_scores/s0/<grid>.csv, columns p_<signal> in [0, 1]) and runs gridshedwatch score my_scores; template: examples/my_method.py.

  • The budget: about 12 watches and 2 warnings per grid per year (median grid); in the alerts track, also no grid above 3 times that.
  • The five reference methods' alerts are published in the alerts format (results/v1.0/alerts), where they reproduce the table above.
  • Random methods submit several seeds; results are averaged.
  • To be listed, open a pull request with your scores or alerts, the code that made them, the --json output, and short answers on the data used and, for the alerts track, which events you looked at while developing. Every result is added, including ones that beat the reference methods. Methods that use extra data, such as weather, are listed separately.

Limits

  • Eight events, seven from two storms (Uri and Elliott). One storm of a new kind could change the picture.
  • Three events shaped the shared rules; five were held out and scored once.
  • Reference methods see only five signals from EIA-930: no weather, outage or market data. The alerts track is open to methods that use more.
  • The baseline covers operators' public notices. Their notices to the industry and their false alarms in ordinary years are not yet compiled.

GridShedWatch grows as new events happen: each load shed that meets the rule is added in a new version and scored with the v1.0 rules.
